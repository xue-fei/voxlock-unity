### 关键结论（踩过的坑）

1. **ONNX 输入必须是 rank-2**：`enroll (1,T)`、`wav (1,S)`。传 1D 会报 `Invalid rank for input`。
2. **Push 的输出缓冲要按 `OutputCapacityFor(count) = count + 512` 分配**。管线会压一窗，追赶时一次能吐出比输入多 512 个样本。
3. **int8 模型不是 bit-exact**：动态量化的激活 scale 取自当前 batch 的数值范围，所以每次推理帧数不同结果会差 ~5e-3（fp32/fp16 只有 3e-7）。用同一份管线代码、只改 framesPerRun 也能复现，证明不是移植错误。需要完全可复现就用 Fp32。
4. **缓冲区扩容必须算上 `_bufStart` 偏移**：只判 `_bufLen + extra` 会在 start 前进后写越界（`Array.Copy` 目标不够长）。
5. 环境：Unity 2021.3.45f2c1 在 `C:/Program Files/Unity/2021.3.45f2c1/Editor/Unity.exe`（**不在 Hub/Editor 下**）。工程被编辑器实例占用时 batchmode 会崩（`HandleProjectAlreadyOpenInAnotherInstance`），需要另建工程 + Assets 目录联接来跑。git 包拉不动时用 `Library/PackageCache` 里的副本改成 `file:` 依赖。

## 修复：OnAudioFilterRead 与 AudioListener 冲突

**报错**：`GameObject has multiple AudioSources and/or AudioListeners attached ... the OnAudioFilterRead
callback of script VoxLockAudioPlayer was first attached to a component of type AudioListener on the game
object Main Camera after which a component of type AudioSource tried to attach it.`

**根因**：`VoxLockAudioPlayer` 自带 `[RequireComponent(typeof(AudioSource))]` 并挂在 Main Camera 上，而 Main
Camera 还有 `AudioListener`。Unity 的 `OnAudioFilterRead` 是**按 GameObject 分派**的，同一个对象上只能有
一个驱动者（AudioSource 或 AudioListener 二选一），先注册的 AudioListener 抢走了回调，AudioSource 的
`Play()` 被拒绝。

**修法**（不是挪场景，是拆组件）：

- 新增 `VoxLockAudioSink`（`[RequireComponent(typeof(AudioSource))]`），只做一件事：把
  `OnAudioFilterRead` 转发给 `VoxLockAudioPlayer.Read()`。
- `VoxLockAudioPlayer` 去掉 `[RequireComponent]`、去掉自己的 `OnAudioFilterRead`，在 `Awake()` 里创建私有
  子物体 `VoxLock Output`（挂 AudioSource + VoxLockAudioSink），播放器本身可以在任何物体上。
- 另建 `VoxLock Clip Output` 子物体给 `PlayClip()`（File 模式整段播放），因为流式那个 AudioSource 的输出
  每个 buffer 都被 filter 覆盖。
- `VoxLockDemo.RunFile` 改调 `Player.PlayClip(clip)`，不再 `GetComponent<AudioSource>()`。

**坑**：`AudioSource.bypassEffects = true` 会连脚本 filter 一起跳过，`OnAudioFilterRead` 永远不触发。只
能设 `bypassListenerEffects` / `bypassReverbZones`。

**校验**：用独立 csproj（netstandard2.1 + Unity 2021.3 的 UnityEngine.CoreModule/AudioModule/UnityEditor
dll）编译全部脚本，0 warning 0 error。注意目标框架必须是 netstandard2.1，用 net472 会因 onnxruntime 依赖
netstandard2.1 而误报（CS1705 + `AsSpan` 找不到）。

**踩坑**：

1. **`VoxLockWavReader.Read` 丢数据**：原实现磁盘按 4096 读，却只 `Array.Copy` `min(want, destination.Length)`
   到目标，其余丢弃。流式路径目标只有 320，直接丢数据。修法：加 `_pending` 待取队列，磁盘读一块重采样后
   先攒着，调用方要多少给多少。块大小 64/128/320/1000/4096/20000 读出序列完全一致（max|diff| = 0）。
2. **WAV 往返误差限值算错**：写用 `v*32767`、读用 `/32768`，系数不对称，误差上限是 **2/32768** 而不是
   1/32768。推导：`|v*32768 - s| ≤ |v| + |v*32767 - s| < 1 + 1 = 2`，所以 `|v - s/32768| < 2/32768`。
   实测 max 3.052e-5，限值取 2.01/32768 = 6.134e-5。
3. **流式文件输出比输入长**：`IsolateFileStreaming` 原来把 `Flush()` 吐出的窗尾也写盘，输出比输入多 384
   个样本，而 `IsolateFile` 走 `Isolate()` 会截断到输入长度。修法：`WriteUpTo()` 把输出限制在「已读入的
   16 kHz 样本数」以内——流的第 i 个输出对应输入第 i 个样本，收尾多吐的那点窗尾不对应任何输入。
4. **`CheckFilePaths` 的 wav 往返比对对象错了**：原来拿「文件路径输出」和「内存里 Isolate 未量化输入的
   结果」比，但文件路径的输入本身是 16 位量化过的 `call.wav`，两者输入不同，差 1.68e-4。改成把文件路径的
   输出再写一遍、读回来比，只测 WAV 层本身。
5. **自检输出目录被 Unity 删掉**：写在 `<工程>/Temp/VoxLockVerify`，Unity 退出时会清理 `<工程>/Temp`，
   `verify_result.txt` 跟着消失。改成 `<工程>/VoxLockVerify`（绝对路径，由 `Application.dataPath` 上溯
   一级得到）。`tools/make_reference.py` 的 OUT 同步改掉。参考文件查找保留 `LegacyOutDir` 回退，让
   已生成的参考文件仍然用得上。

## 音频素材：mp3 转 16 kHz 单声道 WAV

**没有 ffmpeg 也没有 soundfile/scipy/pydub**，只有 numpy。解决办法：`pip install imageio-ffmpeg`，它自带一个
ffmpeg 可执行文件，路径由 `imageio_ffmpeg.get_ffmpeg_exe()` 给出（在
`%APPDATA%\Python\Python313\site-packages\imageio_ffmpeg\binaries\ffmpeg-win-x86_64-v7.1.exe`）。以后要转音频先
想这个包。

**转换**：`Assets/talker.mp3` 本身已经是 16000 Hz 单声道（48 kb/s，40.25 s），所以只是解码成 PCM：

```
ffmpeg -y -i Assets/talker.mp3 -ac 1 -ar 16000 -c:a pcm_s16le Assets/Audio/talker.wav
```

输出 16 kHz / 单声道 / 16 位 PCM，40.16 s，peak 0.857、RMS 0.102。

**素材统一放在 `Assets/Audio/`**：`call.wav`（8 s 合成通话）、`sample.wav`（它的 3 s 声音样本）、
`talker.wav`（40 s 真实语音）。放这里而不是 StreamingAssets 的两个理由：Project 窗口里点一下就能试听；不会
被打进包体。Unity 会把它们按默认设置导入成 AudioClip（Vorbis 压缩），但**不影响管线**——管线走
`VoxLockWav` 直读磁盘上的 16 位 PCM 字节。
